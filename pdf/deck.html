02 · Foundations

A workflow is a graph of
small, honest steps.

A trigger, one or more actions, and the logic that decides which action runs. That is the whole model.

01

Trigger

The event that starts a run: a webhook request, a new email, a schedule, a form submission, or a manual click.

02

Action

A node that does something in the outside world: create a record, send a message, generate a file, call an API.

03

Condition

An IF or Switch node that reads the data and sends each item down exactly one path.

04

Output

The final state: a saved row, a delivered email, a returned HTTP response, a refreshed dashboard.

02 · The universal pattern

Six stages. Every automation
you will ever build.

Different tools, different industries — the shape stays the same. Learning these six stages is what lets you read an unfamiliar workflow and understand it in a minute.

01
Trigger
An event occurs: an email arrives, a form is submitted, a schedule fires. The workflow starts.
02
Data collection
The trigger and follow-up nodes gather the raw payload, attachments, or records needed.
03
Processing
Data is cleaned, parsed, converted, and enriched — text extracted, fields normalised.
04
Decision
Conditions evaluate the data and choose a path: valid or invalid, urgent or routine, in stock or not.
05
Action
The workflow writes, sends, generates, or calls the systems that hold the real business state.
06
Result
A record exists, a customer was informed, a report refreshed — and the execution is logged.

READ IT LEFT TO RIGHT

Each stage hands a defined payload to the next. If a stage has nothing to hand on, the run should stop or branch — not silently continue.

DECISION IS THE HINGE

Without a decision, you have a script. With one, you have a system that can say no, escalate, or wait for a person.

RESULT MUST BE OBSERVABLE

A run that cannot be inspected afterwards is a run you cannot trust. n8n stores the input and output of every node.

03 · Execution lifecycle

What happens when
a workflow runs.

01
The event fires
A webhook receives an HTTP request, a polling trigger finds a new email, or a schedule reaches its time. The trigger node emits the first items.
02
An execution begins
n8n creates an execution record with an ID, a mode (manual or production), and a start time. From here every step is logged.
03
Nodes run in order
n8n walks the graph. Each node receives the items from its upstream node, runs once for the batch, and returns new items.
04
Data is transformed
Expressions read fields, Code nodes reshape objects, Set nodes rename, and Merge or Split nodes change how many items flow on.
05
Logic chooses a path
IF and Switch nodes evaluate the data and send each item to exactly one output. Untaken branches do not execute.
06
The run finishes
A final action writes, sends, or responds. The execution is saved with the input and output of every node, so it can be inspected later.

03 · Decisions & failure

Branches are outputs.
Errors are outputs too.

An IF node has two outputs: true (index 0) and false (index 1). Whatever you connect to each becomes the path that item takes. Nothing else runs.

The run stops here and a person owns the document.

RETRY AT NODE LEVEL

A node can be set to retry on failure with a wait between attempts. Good for a flaky API; useless for a malformed document that will always fail.

ERROR WORKFLOW

An Error Trigger starts a separate workflow when another workflow fails, receiving the error, the workflow name, and the execution URL. This is how failures reach a human.

CONTINUE ON FAIL

A node can pass its error forward as an item instead of stopping the run — useful when one bad row in a batch should not block the other ninety-nine.

RETURNING ERRORS

With Respond to Webhook, the caller gets a JSON error and an HTTP status instead of a silent failure. Bad input should fail loudly.

RETRY WHAT CAN RECOVER

A timeout or a 429 may succeed on the next attempt. A malformed invoice will fail identically every time; retrying it only delays the human.

CAP THE ATTEMPTS

Three attempts with a wait is a policy, not a guess. Beyond it, escalation is cheaper than another call.

KEEP THE FAILURE

Route the failed payload to review with its error message attached. A failure that vanishes is a data loss event.

04 · Building blocks 01–04

Workflows, nodes,
triggers, actions.

Four concepts that answer: what is the automation, what are its steps, what starts it, and what does it do?

01Workflows
A saved graph of nodes and connections, with settings, a name, and an active/inactive state. Exported as JSON.
WHY · It is the unit of automation: versionable, duplicable, and independently testable.
Example · An invoice pipeline, a nightly report, a lead router.
02Nodes
The individual steps. Each has a type, parameters, and a position on the canvas. Core nodes (Code, IF, Set, Merge) and app nodes (Gmail, Sheets, Supabase) share the same execution model.
WHY · Small, single-purpose steps are what make a workflow readable and debuggable.
Example · A Code node formats a job; an IF node tests a condition.
03Triggers
The node that starts a run: Webhook (instant HTTP), Schedule (cron), app triggers such as a Gmail poller, Form, or Manual.
WHY · The trigger decides the latency and the shape of the first payload.
Example · Gmail trigger polling each minute for invoice attachments.
04Actions
Nodes that change something outside n8n: create a row, send a message, generate a file, call an API.
WHY · Actions are where automation becomes business state — and where mistakes become real.
Example · HTTP POST that writes the validated invoice to the ledger.
THE RULE OF ONE JOB
If a node needs the word “and” to describe it, split it. One node that extracts, validates, and saves is a node you cannot test in isolation.
THE MOST COMMON BEGINNER MISTAKE
One enormous Code node that does everything. It works once, and then nobody — including its author — can debug it.
THE SECOND MISTAKE
Hard-coding a credential or an ID inside node parameters. It breaks silently when the environment changes.
THE HABIT THAT SCALES
Name nodes by what they do to the data, not by which app they call. The canvas then reads like a sentence.

Connections, credentials,

How the steps are wired, authenticated, fed dynamic values, and made to decide.

05Connections
Directed edges between node outputs and inputs. Carrying arrays of items, they define execution order and branches.
WHY · The topology is the logic. A misplaced connection silently changes what the automation does.
Example · IF output 0 → retry path; output 1 → escalate path.
06Credentials
Encrypted records holding API keys, OAuth2 tokens, or database logins, referenced by nodes — not pasted into workflow JSON.
WHY · Secrets stay out of exports, screenshots, and version control, and can be rotated once for every node.
Example · A Gmail OAuth2 credential shared by three mail nodes.
07Expressions
Inline formulas in {{ }} that read data from the current item or another node: {{ $json.total }}, {{ $('Node').item.json.id }}.
WHY · The same workflow works for every record instead of one hard-coded example.
Example · Building a request body from the previous node's invoice fields.
08Conditions
IF and Switch nodes that evaluate typed comparisons and route each item to one output.
WHY · They encode the business rule: what is valid, what is urgent, what needs a person.
Example · VAT total equals subtotal plus tax, otherwise flag the document.

Data, executions,

What the workflow actually moves, how you see it move, and how it talks to everything else.

09Data handling
Items are JSON objects (plus optional binary files). Nodes like Set, Code, Merge, Aggregate, and Split Out rename, reshape, combine, or fan out those items.
WHY · Nine out of ten workflow bugs are a field that is one level deeper than the expression expects.
Example · Flattening body.invoice.lines[] into one item per line.
10Executions
A record of one run: status, duration, mode, and per-node input/output. Successes and failures are kept according to the workflow's save settings.
WHY · It is the audit trail. Without it, a wrong number has no traceable origin.
Example · Opening execution #4128 to see the exact model response.
11Error handling
Per-node retry and error-output settings, plus a dedicated Error Trigger workflow that another workflow can call when it fails.
WHY · External APIs fail, documents are corrupt, quotas expire. The workflow must fail in a way someone notices.
Example · Three retries, then a human-review ticket with the job ID.
12Integrations & APIs
Prebuilt app nodes, plus a generic HTTP Request node for any REST endpoint, with auth, headers, query parameters, pagination, and binary bodies.
WHY · It is the escape hatch that means no system is out of reach — and the reason credentials matter.
Example · Posting to a model endpoint and a Supabase REST table from the same workflow.

POLLING

The trigger asks on an interval. Simple, but adds latency and can hit rate limits.

WEBHOOKS

The other system calls n8n the moment something happens. Instant, but needs a reachable URL.

AUTH PATTERNS

API key in a header, bearer token, OAuth2 refresh flow, or a signed internal secret.

05 · Intelligence layer

Same pipeline.
A more capable middle.

Classic automation works when the input is predictable. AI-powered automation keeps the same trigger–action skeleton but adds a node that can read meaning from messy input before the rules run.

HOW A MODEL CONNECTS

An AI node (or a plain HTTP Request node) posts a prompt and the input text to a model API with a credential, and receives text or structured JSON back. n8n orchestrates; the provider infers.

WHAT THE MODEL IS GOOD AT

Reading unstructured text, classifying intent, pulling fields into a schema, summarising, and drafting a reply in a given tone.

WHAT THE MODEL IS BAD AT

Guaranteed arithmetic, authoritative business rules, and knowing when it is wrong. Those stay in nodes you control.

KEEPING A MODEL HONEST
01Ask for a JSON schema and reject anything that does not parse.
02Recompute every number with code; never trust a total from a model.

07.3 · MailFlow

A shared inbox that
knows what matters.

MailFlow reads each incoming message, decides what kind of message it is and how urgent it is, extracts the details a person would need, drafts a reply, and routes the thread — with a human still holding the send button where it counts.

THE PROBLEM

Keyword filters fail on real language. A polite message about a broken delivery and a casual question about pricing look identical to a rule. Urgent matters sit behind routine ones, and staff spend their day sorting rather than answering.

THE SOLUTION

A model reads intent and urgency; the workflow turns that reading into a category, a priority, and structured fields; a Switch routes the thread; a draft is generated for review; and every decision is logged.

Classification decides the path. Confidence decides whether a person is involved.

WHAT IS LOGGED PER EMAIL

Category, urgency, confidence, the extracted entities, whether a draft was approved or edited, and who approved it. This is what makes the inbox measurable.

WHAT IS NEVER AUTOMATED

Sending an unapproved reply to a complaint, promising a refund, or closing a thread. The workflow may prepare those actions; a person performs them.

WHAT HAPPENS WHEN IT IS WRONG

The category is corrected in the log, the thread is re-routed, and the prompt is revised. A misclassification is a process signal, not just an error.

Appendix · Terminology

The words this deck
uses precisely.

Eighteen terms that cover almost every question an audience asks after the demonstration.

Workflow
A saved graph of nodes and connections that n8n executes.
Node
A single step with one job, configured by parameters.
Trigger
The node that starts a run: webhook, schedule, app event, or manual.
Action
A node that changes state in an external system.
Item
One JSON object (plus optional binary) passed between nodes.
Expression
A dynamic value written as {{ }} and evaluated per item.
Credential
An encrypted secret record referenced by nodes, kept out of workflow JSON.
Execution
One recorded run, including per-node input and output.
IF / Switch
Nodes that route items to different outputs by condition.
Webhook
An HTTP endpoint that starts a workflow when called.
Polling
A trigger that checks a source on a schedule instead of being pushed to.
Idempotency
Designing a write so repeating it does not duplicate the result.
Schema
The agreed shape of a data object; what makes validation possible.
Prompt
The instruction and data sent to a language model.
Human-in-the-loop
A deliberate pause for a person to approve or correct.
Error workflow
A separate workflow invoked when another workflow fails.
Sub-workflow
A workflow called as a node by another workflow.
Rate limit
A provider's cap on requests; retries and backoff exist for it.
Backoff
Waiting longer between successive retry attempts.
Payload
The body of data a node sends or receives.
Polling interval
How often a polling trigger checks its source.
Structured output
A model response constrained to a schema so it can be parsed.
Service role key
A high-privilege API key that must never be exposed to a browser.
Endpoint
A specific URL in an API that performs one operation.
Two pairs are worth separating: a trigger starts a run; an action changes something. An execution is one run; a workflow is the definition that produces many. Most confusion in an automation review comes from mixing those up.

Six things worth

01
Automation is a definition, not a tool

A canvas, typed connections, expressions, and an execution log turn a business rule into something that can be reviewed line by line.
03
AI belongs in the middle, not at the top
A model is strongest at reading unstructured input. Keep deterministic checks after it, and keep a person before irreversible actions.
04
The unglamorous parts decide success
Validation, idempotency, retry budgets, and credential handling are what separate a demonstration from a system.
05
Every automation needs an owner
APIs change, models drift, and mailboxes move. A workflow without a named owner is a future incident.
06
The honest measure is effort moved, not magic
These systems do not remove judgement. They move human effort from retyping to specifying, sampling, and approving.
The closing argument: automation is not about replacing people with software. It is about removing the handoffs that make people behave like software — retyping, copying, forwarding — so the judgement stays with the person and the repetition stays with the machine.
